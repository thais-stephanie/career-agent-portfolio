# Privacy model
Reviewed for the integrated public edition, 2026-09-22. This describes implemented paths, not a promise that every feature is offline.

## Local storage
The shared launcher keeps personal Career Agent data in data/personal.db (SQLite): postings, provider payloads, search scores, tracking, notes, your answers to "Does this Search Fit look right?", review state and evidence. User settings live in config/*.local.yaml; atomic settings saves can leave a .backup file. Career Agent reads uploaded PDF/DOCX bytes in memory, extracts text and persists proposals/evidence and provenance, not the original CV file. Extracted personal text is still personal data.

Resumes keeps each profile's resumes, their revisions, job ad snapshots, tailoring runs and findings you set aside in that profile's database, and exported files in `resume_exports/` beside it. An imported PDF or Word file is read in memory and never written to disk; only what you save from it is kept. The previous resume tool, Resume Tailor (retired), left its files in `data/tailor-personal` (first profile) or `data/profiles/<id>/tailor`: they are no longer used and are kept exactly as they were. Moving them into Resumes reads them on this computer, after a verified backup ZIP in `resume_helper_backups/` beside the database; it sends nothing anywhere.

Demo uses data/demo.db and data/demo-config. It never reads the personal workspace or automatically imports a CV, and it sends nothing to an AI provider.

Local profiles (docs/MULTI_PROFILE.md) keep each person's database, private settings and resumes in separate files, so one person's CV, evidence, scores and applications never appear in another's profile. Public job data (postings, descriptions, source payloads, employers, boards, the search index) is kept once, in the shared job catalogue `data/shared/catalogue.db`, which every profile reads. The catalogue holds no profile's data: which searches found a posting, and every score, finding, saved state and note, stay in the profile that made them. Profiles are not accounts and not a security boundary: anyone using the same operating-system account can read every profile's files. A profile's backup holds only that profile; the catalogue has its own backup.

On Windows, the Career Agent shortcut opens Microsoft Edge in app mode with its own browser data in `data\app-window` inside the Career Agent folder: Edge's cache, local storage and settings for that window, never your usual Edge profile. Career Agent itself makes no network connection when the shortcut opens it. Edge does: in testing, the app window's Edge processes opened eight HTTPS connections to Microsoft addresses within 20 seconds, as any Edge window does, although the window is started with Edge's background networking, component updates and sync turned off. Without Edge, the shortcut uses your usual browser. The shortcut itself holds only the path of the Career Agent folder. Links that leave Career Agent from that window, such as a job's own page, open in Edge windows that use the same Career Agent browser data, without your usual Edge profile's saved passwords; Career Agent keeps running until those windows close too. Browser local storage holds presentation preferences such as language, filters and selected candidate. There is no application telemetry or analytics SDK in either product. Data is not encrypted by the application. Operating-system accounts, disk encryption and backups control access to local files.

## Network paths
| Action | What can leave the computer |
|---|---|
| First installation | Requests to GitHub for uv and Python distributions, and package indexes for locked Python dependencies. These services see normal connection metadata. |
| Browsing existing local data / deterministic tailoring | Requests only to the local server; no AI provider is needed. Fonts and frontend assets are bundled. |
| Collecting or discovering jobs | Requests to configured job boards and employer sites, including query parameters and ordinary connection metadata. Career Agent does not attach your CV or confirmed evidence to collection. Source permissions and request limits still apply. |
| Targeted searches and employer boards | A Himalayas refresh also runs a bounded number of searches (24 by default): each sends one search phrase, taken from your role anchors or your work phrases, and one country code from your eligible markets. Nothing else from your search settings, and never your CV, profile or evidence. Employer board discovery asks Ashby, Greenhouse and Lever whether a board exists under a name derived from an employer already seen on an aggregator; it sends that guessed board name only. |
| LinkedIn via JobSpy (experimental, off by default) | Only after the person switches it on for their own profile in Settings & Sources, having read that LinkedIn restricts automated collection. Each run sends LinkedIn's public guest job search a bounded number of short searches (one search phrase from role anchors or work phrases, and one place each; up to three result pages each) and then reads a limited number of public posting pages, from this computer's own connection, with the browser-like headers python-jobspy sends. It never signs in and never asks for or stores a LinkedIn password, cookie or session. Nothing about the CV, profile or evidence is sent. |
| Opening an employer link | Your browser visits the external website. Its privacy policy, cookies and browser settings apply. |
| Career Agent semantic matching (optional) | Only when you start a semantic run: your search intent phrases (the work, tools and other signals you want) and the title and text of each selected posting go to the provider you chose or Auto chose: DeepSeek with your API key, or your own signed-in Claude Code or Codex using your subscription. Never your Career Profile, evidence, CV files, application history, other postings or the database. Each run is capped; a metered run shows an estimate and stops at its budget. The DeepSeek key lives only in the root `.env`, never in the database or an API response. Demo mode never uses it. See SEMANTIC_MATCHING.md. |
| Career Agent Ollama action | Posting text goes to the explicitly selected local Ollama service, normally port 11434. Its client refuses non-loopback endpoints, and the reading path imports no hosted-provider code, so there is no fallback to a cloud model (a test checks both). Cancel closes the connection, which makes Ollama stop. Model downloads, if needed, are separate operations. |
| AI drafting and review in Resumes (optional) | Only when you press **Tailor with AI** or ask for a review: the job's title and company, the asks it quotes that you have support for, and the resume lines and confirmed statements relevant to them go to the provider set in AI & Semantic Matching. Never contact details, dates, other jobs, applications, Search Fit or settings; the ad is never sent whole. The screen names the provider and what it receives first; demo mode sends nothing. |
| Advanced Career Agent extraction CLI | Explicit execution flags permit sending selected posting text to configured hosted providers. This is not part of normal browsing or the release tests. |

The release tests make no live AI call. The semantic matching benchmark did, once, on the maintainer's machine (SEMANTIC_MATCHING.md). Do not use the phrase 'nothing leaves your computer' to describe all configurations.

## Handoff and provenance
Opening Resumes from a posting puts only that posting's id in the local address; no posting text, CV, evidence or note is ever in a URL. An old Resume Tailor link (`/resume-tailor?job=<id>`) is answered the same way: the id is checked and Resumes opens. A resume line cites a confirmed Career Profile statement by its key, and is re-checked against what is confirmed now whenever it is exported.

## Exports and backups
DOCX and JSON are generated locally. PDF is printed by a locally installed Microsoft Edge (or Chrome), headless, with a throwaway browser profile in a temporary folder that is removed afterwards; your own browser profile is never used. The application does not use a cloud PDF conversion service. Operating-system or office-suite sync settings are outside the app's control.

The verified backup made before moving the old Resume Tailor's resumes is a ZIP of that workspace beside the profile's database; `forget everything` deletes it with the resumes, and never the old workspace itself. Career Agent backup includes one profile's database and private configuration, excluding credential files; once the installation uses the shared catalogue, that database holds no postings and the manifest says so. `career-agent backup --catalogue --profile NAME` archives the shared catalogue, which holds public job data only. The Search Fit feedback export is a private CSV of your answers and notes about scores, with each posting's title, company, source and URL; the answers change no score and are deleted by `career-agent forget tracking`. Manual copies of data/ and config local files are also private. Export and backup files are not encrypted by the application. Never attach them to a public issue without reviewing their content.

## Local HTTP protections
Default address: Career Agent http://127.0.0.1:8765, one server for everything, Resumes included. The launcher binds it before opening a browser and refuses a conflict. Career Agent enforces loopback, Host/Origin checks and JSON mutations. No permissive CORS policy is enabled. These services are for a trusted local user, not an authenticated multi-user or internet-facing deployment. A malicious local process can access them.
