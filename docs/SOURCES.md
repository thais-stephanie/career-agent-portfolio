# Source permissions
Collection is a deliberate user action, separate from local browsing. config/source_catalogue.yaml records supported sources and permission observations; these observations are dated, not guarantees that a vendor's policy will never change. Review current vendor terms before adding or changing a connector. Respect explicit prohibitions, request budgets, rate limits and employer link-back requirements.

Discovery identifies a board. Collection reads it. Neither a guessed board identity nor a remote label proves hiring eligibility. A source with only metadata must not be represented as a fully analyzed posting. See src/career_agent/providers and src/career_agent/net for the implementation, and the connector regression fixtures under tests/fixtures/providers.

Protocol fixtures also include recorded public vendor responses needed for adapter regression tests. They are not candidate CVs, application history, the production database or a redistributed job catalogue. Demo screenshots use only evaluation/demo and the Tailor synthetic candidate. New fixtures should be minimal, synthetic where possible, and free of tracking parameters and personal contact details.

## Coverage: two lanes, one corpus
The exploratory lane is every broad collector: feeds and every employer board the workspace knows. The targeted lane is a bounded set of searches built from the person's role anchors, their aliases and their work phrases, asked in each market scope the eligibility settings imply (a country, a region, worldwide). Both lanes write one deduplicated corpus. `job_retrieval_lane` records which postings a targeted search returned, with the query and the origin of its term, so the lanes can be measured against each other. It is provenance only: nothing that decides eligibility or computes Search Fit reads it.

Market scopes are related search scopes, not synonyms. Asking for Brazil, Latin America and worldwide are three different questions whose answers overlap, and the eligibility gate still decides each posting on its own text.

The ATS registry in config/companies.yaml is synced into the database on launch and at the start of Refresh all. The sync is additive: it never reactivates or edits a board already held. Employer board discovery then looks for the Ashby, Greenhouse or Lever board of employers already seen on aggregators, employers surfaced by targeted searches first. A board is registered only when it lists a posting title the aggregator showed for that employer, and every employer's answer is recorded so it is never probed twice.

`career-agent source-coverage` prints the per-source funnel (boards, last attempt and success, status, requests, fetched, new, updated, deduplicated, failed, canonical and open jobs, and why a run was partial). It changes no posting and makes no network call. A source whose last success is older than 72 hours shows as Stale; a run that stopped at a page limit, a request budget or a source ceiling shows as Partial with that reason.

## Experimental local overrides (LinkedIn via JobSpy)
Some sites forbid automated collection. LinkedIn's robots.txt prohibits automated access without express permission, so its catalogue row stays FORBIDDEN, says so, and `can_refresh` refuses it for every profile that has not opted in. That row also declares an `experimental_override` (the `linkedin` adapter, through python-jobspy). It is a local exception the person using a profile may choose, never a reinterpretation of the rule:

- Off by default, for every profile, and never switched on by a shipped file or a new profile.
- Switched on only in Settings & Sources, after a plain warning: LinkedIn restricts automated collection and opting in does not change that; it may rate-limit or block the requests; results can be partial; coverage is never complete; Career Agent never signs in or stores a LinkedIn password, cookie or session. The choice, with the warning version and time, is stored in that profile's database (`candidate_state`). A materially new warning requires a new choice.
- Query-driven and bounded: the targeted plan (role anchors, their aliases, work phrases) times the market scopes, 24 searches of 25 cards by default, paced 3 to 6 seconds apart. A search reads up to three result pages (JobSpy pages ten cards at a time, 3 to 7 seconds apart), so 24 searches are at most about 72 requests. Posting pages are read only for postings the corpus does not hold (then for held ones still missing their text), most-asked first, capped at 60 per run, 2 to 4 seconds apart. The home-market "Remote" scope is not asked: measured, LinkedIn's guest search ignores the remote filter and returned the same postings as the country scope.
- Honest about refusals: python-jobspy reports a LinkedIn 429 only in a log line and swallows posting-page errors, and by default retries a 429 three times. The adapter instead drives JobSpy's LinkedIn scraper on its own session with no automatic retries and records every response's status. A 429, LinkedIn's 999 or a 403 (or a redirect to the sign-in page) is a refusal: a refused search is retried once after 30 seconds and then ends the run; three failed searches in a row end it; a refused posting page, or three unreadable ones in a row, end the page reading. A run whose searches were all refused is FAILED, never "no jobs". Runs record planned, attempted, succeeded, empty, failed and refused searches, retries, requests, raw and unique results, new, seen-again, completed-later and deduplicated jobs, and page reads attempted and succeeded.
- Deduplicated against the corpus: an employer apply link a board adapter already holds, or identical text from the same employer for the same title, is recorded as a sighting of that job, not a second row, and its page is not read again on later runs.
- Switching it off in Settings stops a run in progress before its next search or page read.
- python-jobspy pins numpy 1.26.3, which ships wheels only up to Python 3.12 (the launcher's version). It is declared for Python 3.12 only; elsewhere the source says it is unavailable.
- Upstream JobSpy sends browser-like request headers. They are not changed, and no proxy or rotation is used.
