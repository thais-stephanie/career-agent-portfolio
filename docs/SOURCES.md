# Source permissions
Collection is a deliberate user action, separate from local browsing. config/source_catalogue.yaml records supported sources and permission observations; these observations are dated, not guarantees that a vendor's policy will never change. Review current vendor terms before adding or changing a connector. Respect explicit prohibitions, request budgets, rate limits and employer link-back requirements.

Discovery identifies a board. Collection reads it. Neither a guessed board identity nor a remote label proves hiring eligibility. A source with only metadata must not be represented as a fully analyzed posting. See src/career_agent/providers and src/career_agent/net for the implementation, and the connector regression fixtures under tests/fixtures/providers.

Protocol fixtures also include recorded public vendor responses needed for adapter regression tests. They are not candidate CVs, application history, the production database or a redistributed job catalogue. Demo screenshots use only evaluation/demo and the Tailor synthetic candidate. New fixtures should be minimal, synthetic where possible, and free of tracking parameters and personal contact details.

## Coverage: two lanes, one corpus
The exploratory lane is every broad collector: feeds and every employer board the workspace knows. The targeted lane is a bounded set of searches built from the person's role anchors, their aliases and their work phrases, asked in each market the person chose under "Which markets do you want to search first?" (`regions.target`: a region, a country, or worldwide), and in one worldwide scope when none is chosen. Where the person lives and where employers may hire them from never choose a scope: those answer a posting's requirements (ADR-0032). The query budget bounds the plan however many markets are chosen. Both lanes write one deduplicated corpus. `job_retrieval_lane` records which postings a targeted search returned, with the query and the origin of its term, so the lanes can be measured against each other. It is provenance only: nothing that decides eligibility or computes Search Fit reads it.

Market scopes are related search scopes, not synonyms. Asking for Brazil, Latin America and worldwide are three different questions whose answers overlap, and the eligibility gate still decides each posting on its own text.

The chosen markets also set the refresh ORDER, never the set: their sources run first, then worldwide boards, then every other board. No source is paused for covering another market; only a pause the person chose in Settings & Sources leaves one out. Choosing markets changes no match, so it asks for no recalculation.

The ATS registry in config/companies.yaml is synced into the database on launch and at the start of every refresh run. The sync is additive: it never reactivates or edits a board already held. Employer board discovery then looks for the Ashby, Greenhouse or Lever board of employers already seen on aggregators, employers surfaced by targeted searches first. A board is registered only when it lists a posting title the aggregator showed for that employer, and every employer's answer is recorded so it is never probed twice.

## Refreshing: one plan for every button
Find jobs, Refresh due sources, Refresh all available sources and a source's own Refresh now all run the same orchestration (`web/source_refresh.py`). At the press it reads each source's freshness, decides the plan and freezes it: Find jobs and Refresh due sources take the sources that are due (never refreshed, refreshed more than a day ago, or failed and past their wait); Refresh all available sources takes every available one; Refresh now takes exactly one. A blocked source, an experimental source the profile has not switched on, and a site still inside the wait after refusing requests are never in any plan; a paused source is in none except its own Refresh now, which the person pressed for it. The run's total is the number of sources in its plan: an employer-board family counts once, however many employer boards it reads, and a `source_board` row is never a source. A source that turns fresh or due while the run is going changes the next press, not this run's total. When the run ends, the new and changed postings are scored by the normal targeted rescore, and the run records how many jobs it added, which is what Home's "New" shows.

Freshness and completeness are separate. A source refreshed an hour ago is fresh even when that refresh read only part of it, and a partial run says why: a batch read by design that the next refresh continues (Himalayas, Speedrun, Programathor, Dynamite Jobs); a request budget whose next refresh continues with the slices left (Jobgether); our own page limit that the next refresh reads again (Get on Board, Arbeitnow, Gupy's pages); a ceiling of the source's own interface that no refresh will pass (Gupy's offset wall; Speedrun serves at most 201 pages of the 22,000 it lists); or some employer boards that failed while the rest were read ("121 of 124 employer boards refreshed, 3 failed").

Sources that continue keep their place in their own run record, never in a table of their own and never with anything about the person: Himalayas keeps the feed's keyset cursor (newest first, so a kept cursor still means "older than this") and reads 50 pages of 20 below the newest pages each refresh; Speedrun reads 4 pages of 50 further down with one page of overlap and starts a new lap at the interface's ceiling; Programathor reads 3 further listing pages, does not ask again for a posting it already holds, and skips for one refresh a posting that failed the last time. A kept place that is malformed or refused costs a lap, never the refresh. 4 Day Week reads its whole feed (about 256 pages of 100 at a request every 1.1 seconds, under the documented 60 a minute), bounded at 300 pages.

`career-agent source-coverage` prints the per-source funnel (boards, last attempt and success, status, requests, fetched, new, updated, deduplicated, failed, canonical and open jobs, and why a run was partial). It changes no posting and makes no network call. A source whose last success is older than 72 hours shows as Stale; a run that stopped at a page limit, a request budget or a source ceiling shows as Partial with that reason.

## Experimental local overrides (LinkedIn via JobSpy)
Some sites forbid automated collection. LinkedIn's robots.txt prohibits automated access without express permission, so its catalogue row stays FORBIDDEN, says so, and `can_refresh` refuses it for every profile that has not opted in. That row also declares an `experimental_override` (the `linkedin` adapter, through python-jobspy). It is a local exception the person using a profile may choose, never a reinterpretation of the rule:

- Off by default, for every profile, and never switched on by a shipped file or a new profile.
- Switched on only in Settings & Sources, after a plain warning: LinkedIn restricts automated collection and opting in does not change that; it may rate-limit or block the requests; results can be partial; coverage is never complete; Career Agent never signs in or stores a LinkedIn password, cookie or session. The choice, with the warning version and time, is stored in that profile's database (`candidate_state`). A materially new warning requires a new choice.
- Query-driven and bounded: the targeted plan (role anchors, their aliases, work phrases) times the market scopes, 24 searches of 25 cards by default, paced 3 to 6 seconds apart. A search reads up to three result pages (JobSpy pages ten cards at a time, 3 to 7 seconds apart), so 24 searches are at most about 72 requests. Posting pages are read only for postings the corpus does not hold (then for held ones still missing their text), most-asked first, capped at 60 per run, 2 to 4 seconds apart. The home-market "Remote" scope is not asked: measured, LinkedIn's guest search ignores the remote filter and returned the same postings as the country scope.
- Honest about refusals: python-jobspy reports a LinkedIn 429 only in a log line and swallows posting-page errors, and by default retries a 429 three times. The adapter instead drives JobSpy's LinkedIn scraper on its own session with no automatic retries and records every response's status. A 429, LinkedIn's 999 or a 403 (or a redirect to the sign-in page) is a refusal: a refused search is retried once after 30 seconds and then ends the run; three failed searches in a row end it; a refused posting page, or three unreadable ones in a row, end the page reading. A run whose searches were all refused is FAILED, never "no jobs". Runs record planned, attempted, succeeded, empty, failed and refused searches, retries, requests, raw and unique results, new, seen-again, completed-later and deduplicated jobs, and page reads attempted and succeeded.
- Deduplicated against the corpus: an employer apply link a board adapter already holds, or identical text from the same employer for the same title, is recorded as a sighting of that job, not a second row, and its page is not read again on later runs.
- Switching it off in Settings stops a run in progress before its next search or page read.
- Searched by role, never by skill: the terms are the named role anchors, at most 12 role-family aliases and at most 4 work phrases (20 when no role is named). Tool signals are score evidence after retrieval, not search terms, and Career Evidence is never read to plan a search: a profile listing 200 tools makes as many searches, with the same terms, as one listing 10 (`tests/unit/test_linkedin_plan_invariant.py`). A work phrase is a responsibility the person described, so a phrase that also names a tool can be one of those 4 or 20 terms; the number of searches stays capped either way. Benchmarked on 2026-09-26 from the runs already recorded, with no new request (the source was cooling down after a refusal): anchor searches produced the densest results (72% GOOD or STRONG among postings with text, 56% STRONG), aliases added postings the anchors missed at 62% GOOD or STRONG, and work phrases added the most postings at 56%. The plan was kept as it is. Denominators are the postings whose text was read (about 40 each for anchors and aliases), so these are indications, not measurements of LinkedIn's market.
- python-jobspy pins numpy 1.26.3, which ships wheels only up to Python 3.12 (the launcher's version). It is declared for Python 3.12 only; elsewhere the source says it is unavailable.
- Upstream JobSpy sends browser-like request headers. They are not changed, and no proxy or rotation is used.

### Indeed, Glassdoor and Google through JobSpy: reviewed 2026-10-08, not built
python-jobspy 1.1.82 can also search Indeed, Glassdoor and Google. Each was reviewed under the collection policy (ADR-0018: what is not explicitly prohibited may be collected; an explicit prohibition in the terms or in robots.txt for the route used is obeyed; a technical block is never bypassed and is never a basis either way). Terms, robots.txt and technical blocks are recorded separately in each catalogue row's `policy_review`, with URLs, dates, quotes, the conclusion per route and its certainty; `policy_problems` in `sources/catalogue.py` checks every reviewed row against the policy, and a re-review with new evidence is an edit to that row.

| Source | Terms (read 2026-10-08) | robots.txt for the library's route (`*` group: every JobSpy user agent is a browser string) | Technical blocks seen | Conclusion |
|---|---|---|---|---|
| Indeed | indeed.com/legal (updated 2026-09-29): no "automated system (bots, scrapers, spiders, AI or Agentic AI) to access, data-mine ... without Indeed's express written permission"; "You may not crawl, scrape, extract data from ... any part of the Site". Covers reading jobs; applying is a separate clause. Same in br.indeed.com/legal | `apis.indeed.com/robots.txt`: `Disallow: /` | none tested | prohibited, HIGH (terms + robots). The site's own search pages (not the library's route) are allowed to crawl by robots.txt, but the terms forbid extraction: prohibited, MEDIUM |
| Glassdoor | GAP: all five official URLs answered 403; not read, not used | `glassdoor.com/robots.txt`: `Disallow: /graph`, the path the library POSTs to | 403 on the terms pages (2026-10-08) and on a listing (2026-09-11) | prohibited, HIGH (robots alone) |
| Google | policies.google.com/terms (effective 2026-07-30) forbid "using automated means to access content ... in violation of the machine-readable instructions on our web pages (for example, robots.txt files ...)" | `google.com/robots.txt`: `Disallow: /search` | none tested | prohibited, HIGH (terms + robots) |

The Indeed Brasil row used to quote "o uso de qualquer automacao, script ou bots"; that clause is about automating applications. It now quotes the clause that covers reading jobs. The LinkedIn override is the owner's single, named exception and is not a precedent for these. Each stays a link the person opens in a browser. All three are REEVALUABLE: a new review on new first-party evidence (the terms or robots.txt changing, Glassdoor's terms becoming readable) or an applicable authorization (written permission, a documented feed) reopens them by editing the row's `policy_review`; `policy_problems` then requires the row to leave BLOCKED when no route is prohibited.
